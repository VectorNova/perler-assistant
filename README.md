# 拼豆辅助 · Perler Beads Assistant

上传一张**现成的拼豆图纸**（PNG/JPG），自动识别网格与色号分布，
点哪个颜色就高亮它的全部分布，再按「一种颜色 → 一粒一粒」的顺序指引你拼完。

> 灵感与色号数据来自 [Zippland/perler-beads](https://github.com/Zippland/perler-beads)（AGPL-3.0）。
> 那个项目是「**图片 → 生成图纸**」；本项目把它的「专心拼豆」那部分单独拿出来，
> 并把入口换成「**直接上传已有图纸**」，不参与图纸生成。

---

## 快速开始

```bash
npm install
npm run dev          # 开发模式，默认 http://127.0.0.1:5178
```

生产构建与预览：

```bash
npm run build
npm run preview      # http://127.0.0.1:4173
```

打开后在首页点「标准图纸」等示例按钮即可立刻试跑（示例图在 `public/samples/`）。
也可以用 URL 直接进：

| URL | 效果 |
| --- | --- |
| `/?demo=a` | 载入示例图纸 a，停在网格校准页 |
| `/?demo=a&auto=1` | 载入并自动识别，直接进工作台 |

## 功能

### 1. 上传 + 网格校准
- 拖拽或点击选择 PNG / JPG / WebP / GIF / BMP。
- 自动识别格距、原点、行列数（支持**小数格距**，导出图未必是整数像素格）。
- 识别不准时可以手动改：格宽 / 格高 / 原点 X,Y / 列数 / 行数，
  或用「移动网格」直接拖动、方向键微调（Shift + 方向键 = 10px）。
- 实时预览会显示「识别出多少种颜色、多少粒豆子、多少空格」，一眼就能看出有没有对上。

### 2. 项目管理（首页）

首页就是项目列表，**图纸、参数、拼豆进度全部保存在本机浏览器里**（IndexedDB），
中途停下关掉页面，下次打开接着拼。

- **项目卡片**显示：缩略图、名字、网格尺寸、颜色数、豆子数、进度条 + 百分比、
  已拼/总数、更新时间、图纸文件名。
- **封面用的是「识别结果成品图」**，不是上传图纸的缩略图 ——
  从 `cells` 直接按 1 像素 1 格画出来再缩放，所以是**纯色块、没有网格线、没有格内色号、
  也没有红色分区线**，一眼就能认出是哪个图案。
  而原图缩略图缩到 84px 就是一团糊，还依赖 Blob 解码（失败或旧版本迁移过来的项目
  就只能显示「无缩略图」）。旧项目打开时会自动补画一张封面。
- **当前总进程**：首页左上角汇总所有待完成项目的累计进度。
- **三个分类（带数量）**：
  - **待完成**：还没拼完的项目
  - **已完成**：拼到 100% 会自动归到这里（**也会一直保存，不会被删**）；
    也可以手动「标记完成 / 取消完成」来回搬
  - **识别失败**：识别得不理想的项目。点卡片上的「识别失败」归类进来，
    这里可以「**全部删除**」一键清理
- **重命名**：默认名是「项目1、项目2…」，点卡片上的 ✎ 改成图纸的名字方便管理。
  点重命名时如果还是默认名、且存了图纸文件名，会**自动把文件名填进去**当初值。
- **删除**：卡片上「删除」→ 二次确认「确认删除」。会连同图纸原图、识别数据、
  进度一起删掉。
- **重新校准**：不用再上传一次！图纸原图存在项目里，点「重新校准」直接回到校准页，
  确认后**覆盖原项目**而不是新建。

### 数据是怎么存的

用 IndexedDB 而不是 localStorage，原因是：

- 要保存**图纸原图**（几百 KB 的 JPEG）。localStorage 只有 ~5MB 且只能存字符串，
  base64 还会再胖 33%；IndexedDB 能直接存 Blob。
- localStorage 存 TypedArray 必须先 base64，IndexedDB 可以**结构化克隆直接存**。

拆成 4 个 object store，**首页只读最小的那个**：

| store | 内容 | 为什么单独放 |
| --- | --- | --- |
| `projects` | 元信息 + 全部显示参数 + 缩略图 | 首页只读它。一张 104×104 的识别数据约 70KB，混在一起的话列 20 个项目要反序列化 1.4MB+ |
| `patterns` | 识别结果（grid / cells / blank / purity） | 只有打开项目时才读 |
| `progress` | 已完成标记 | 每点一格都要写，单独放写入开销最小 |
| `images` | 图纸原图 Blob | 只用于缩略图和重新校准 |

两个容易踩的坑，都已经在代码里注明：

1. **meta 的读-改-写必须在同一个事务里**（`updateMeta`）。
   之前是「先 `await getProjectMeta()` 读，再开一个事务写」，两次事务之间
   别的更新（参数防抖保存、进度防抖保存、色板约束重识别）也会读到同一份旧值，
   后写的那个把先写的改动整片覆盖。
   实测症状：应用色号约束后项目里颜色数已经是 32，但首页卡片还显示 53。
2. **进度写入要串行化**。`done` 每次点格子都变，用 700ms 防抖 + 「写的时候只记一个
   待写标记，写完立刻再写最新值」，避免并发写导致旧数据覆盖新数据；
   另外切到后台/关页面时会强制写一次。

> 旧版本的单会话进度（`localStorage` 里的 `perler-assistant/session/v1`）
> 会在第一次打开时**自动迁移**成一个项目「…（从旧版本导入）」，不会丢。

## 手机端

手机上是**另一套布局**（`App.tsx` 里走 `if (isMobile)` 分支，但和桌面端共用同一批
组件实例变量，所以逻辑只有一份）。

原因：桌面三栏在 360px 宽的手机上竖着堆起来有 932px 高，而视口只有 690px ——
要来回滚 300 多像素，一边看图纸一边看指引等于废了。实测数据：

```
视口 390×844        桌面三栏竖排后      手机端新布局
文档总高 1067px ←   （要滚 377px）     文档总高 844px（不滚）
画布 / 抽屉 / 面板  380 / 276 / 276     604 / 138
```

新形态是「**画布占满 + 底部抽屉**」：

- 顶栏压缩成一行：返回首页 / 项目名 / 进度百分比
- 画布占据主体（844px 视口里占 604px），**没有悬浮工具条挡图案**
  （缩放靠双指捏合，画布条上还有「适应」）
- 底部抽屉**标签栏常驻**：指引 / 颜色 / 显示 / 图纸
- 抽屉**收起时**只留拼豆最关键的三个信息，不用展开就能操作：
  当前色号色块 + 「第 N/M 种 · 第 i/j 块 · X 粒」 + 大按钮「✓ 这一块拼好了（X 粒）」
- 点非「指引」的标签会自动展开；点已激活的「指引」才在展开/收起之间切换
- 手机上不需要单独的「看颜色分布 / 开始拼豆指引」模式切换：
  「颜色」标签就是看分布，「指引」标签就是拼豆指引
- 「网格 / 色号 / 分区线」三个开关在手机端从画布条移进了「显示」抽屉，省一行高度
- 按钮触摸高度放大（大按钮 54px，缩略按钮 ≥34px）
- `height: 100dvh`（地址栏收放时 `100%` 会算错）、`overscroll-behavior: none`
  （画布上拖拽不触发下拉刷新）、`env(safe-area-inset-bottom)`（避开 iPhone 底部横条）

触摸交互本来就是支持的：`.pattern-canvas` 上有 `touch-action: none`
（否则浏览器会把拖拽抢去滚页面），双指捏合缩放和单指平移已经实现。

### 怎么在手机上打开

#### 方式一：静态托管 + PWA（推荐 —— 手机完全独立，不需要电脑）

**https://vectornova.github.io/perler-assistant/**

这是真正满足「去拼豆时不可能带电脑」的方案。关键不是「手机能一直连上服务器」，
而是 **service worker**：

1. 在家 WiFi 下打开一次，SW 会把整个 app（含图标和示例图纸，约 3.5 MB）预缓存到手机本地
2. 浏览器菜单里选「**添加到主屏幕**」，得到一个带图标的独立入口
3. 之后**飞行模式也能用** —— 去拼豆时不需要电脑、不需要网络

> 之所以特别强调这点：`github.io` 在国内访问时常不稳。但离线方案下你只需要
> **一次性连得上**，之后就完全走本地缓存，稳定性问题就绕开了。

部署是自动的：`.github/workflows/deploy-pages.yml` 在每次 push 到 `main` 时构建并发布。
仓库页面的地址是 `https://<user>.github.io/<repo>/`，所以构建时必须带 `BASE_PATH`：

```bash
BASE_PATH=/perler-assistant/ npm run build   # Windows: $env:BASE_PATH='/perler-assistant/'
```

不带 `BASE_PATH` 就是普通的根路径构建，本地 `npm run preview` 用。

#### 方式二：局域网直连（临时调试用，需要电脑开着）

```bash
npm run build
npm run preview:lan        # 监听 0.0.0.0:4173
```

手机浏览器打开 `http://<电脑局域网IP>:4173`（`ipconfig` 查 IPv4；同一个 WiFi；
Windows 防火墙可能要放行 Node）。

> 局域网是 **HTTP 非安全上下文**，所以**实时摄像头用不了**
> （`<input type="file" capture>` 仍然可用，那只是文件选择器）。
> 要 HTTPS、要能装到主屏幕并离线打开，就部署到静态托管
> （Cloudflare Pages / Vercel / Netlify 拖 `dist` 上去，免费 HTTPS）。

### 实测性能

CDP 的 CPU 降频 + 手机视口（`npm run bench`）：

| 降频 | 自动识别 → 工作台 | 按格数校准 → 工作台 |
| --- | --- | --- |
| 1x（本机） | 91 ms | ~86 ms |
| 4x（中端安卓） | 263 ms | ~417 ms |
| 6x（低端机 / 老 iPhone） | 466 ms | ~565 ms |

以上为旧版仅颜色识别的基准，不包含新增的原图字符识别。
新导入保留原生像素，小字不会先被缩小；6400 万像素以上的图片会要求先裁掉图纸外区域。
像素分块读取，校准预览单独缩小并保留原图坐标，避免一次创建过大的手机画布。
大图占用更多内存，手机上优先使用原始电子图，并裁掉无关留白，避免缩小格内文字。

## 图标与品牌

Logo 原图放工作区根目录，用脚本生成整套图标：

```bash
npm run icons        # = tools/make-icons.ps1 -Source "../图标.png"
```

脚本做的事：

1. **找透明包围盒**。原图 1254×1254、背景全透明，内容只占 837×741，
   四周有 200+ px 空白 —— 不裁掉的话图标里会有大片空白，小尺寸下更糊。
2. **合成到白底**再缩放。这不是随手选的：透明图直接做双三次缩小时，
   完全透明像素的 RGB=0,0,0 会混进边缘、产生**深色描边**（straight alpha 的经典问题）。
   应用里所有表面都是白的，合成到白底视觉上一样，还顺便避开描边。
3. 按用途调整内容占比：

| 文件 | 尺寸 | 内容占比 | 用途 |
| --- | --- | --- | --- |
| `favicon-16/32/48.png`、`favicon.ico` | 16/32/48 | 0.92~0.96 | 浏览器标签。小尺寸没地方留白，贴近边缘 |
| `logo-96.png` | 96 | 0.94 | 应用内顶栏 / 大标题 |
| `apple-touch-icon.png` | 180 | 0.86 | iOS 加到主屏幕 |
| `icon-192/512.png` | 192/512 | 0.84 | Android / PWA 清单 |
| `icon-maskable-512.png` | 512 | **0.58** | Android 自适应图标：系统会裁成圆形/方形，只保证内部 80% 安全区，所以内容要缩更多 |

`favicon.ico` 是手工拼的 ICO 容器（PNG 载荷，现代浏览器都支持），装了 16/32/48 三个尺寸。
回归测试会校验它的魔数 `00 00 01 00` —— 写错一个字节浏览器就静默不显示，很难查。

`index.html` 里除图标还加了：

- `viewport-fit=cover` —— **这是 `env(safe-area-inset-*)` 生效的前提**，
  手机端底部抽屉避开 iPhone 横条就靠它
- `apple-mobile-web-app-capable` —— iOS 加到主屏幕后全屏显示（不需要 service worker 就生效）
- `theme-color` + `manifest.webmanifest` —— Android 加到主屏幕时用对图标和名字

> 目前**还没有 service worker**，所以不是完整 PWA：能装到主屏幕、图标名字都对、
> iOS 还能全屏，但**离线打不开**，Android 也不会弹安装横幅。要那些得补 SW（需要 HTTPS）。

> 更新：**service worker 已经加上了**（见下面的「手机端」一节），
> 上面这段是当时的状态，保留作记录。

### 3. 看清颜色分布
- 左侧列出全部颜色：色块、色号、HEX、粒数、已拼进度。
- **点任意颜色，图纸上只剩这个颜色是原色，其它颜色被压暗**，分布一目了然。
- 非选中颜色的处理方式可切换：压暗 / 转灰度 / 完全隐藏。
- 「点击颜色时自动缩放到该颜色范围」可以快速跳到零散小区块。

#### 画布上的显示约定

这些都是踩过坑之后定下来的，几个约定不要随手改：

| 元素 | 画法 | 为什么 |
| --- | --- | --- |
| **当前色块** | 沿色块真实边界描一圈：白色粗底 + 亮红主线 | 早先只用半透明蓝色平铺，而其它格子已经被压暗成灰蓝，两者几乎分不出来。描边在 3px/格 时仍然认得出 |
| **已完成格子** | 中性压暗（`rgb(15,23,42)`，~52% 不透明）+ 黑底白对勾 | 早先用半透明**绿色**蒙版，压在大片浅蓝格子上会形成一大块绿，和未完成区域撞色、很影响观感。中性色不引入任何色相 |
| **分区线** | 随缩放加粗（`max(1, 格宽×0.08)`）+ 白色描边打底 | 固定 1.5px 不随缩放变化，放大后相对格子就"消失"了；白底保证压在任何格色上都看得清 |
| **坐标尺** | 贴图纸上/左边缘的蓝色数字标签，每 `sectionInterval` 格一个；图纸边缘滚出视野时钉在视口边缘 | 放大后分区线会滚出视野，靠它随时知道自己在第几行第几列 |
| **低置信度格子** | 左上角一个小三角，且只取「最差的一小撮」 | 早先按固定阈值 0.55 标「整格虚框」，而高密度图纸**每一格**纯度都低 —— 10816 格里标了 10450 格，整块画布被橙色虚线淹没，连分区线都看不见了。现在改为按纯度排序取最差 2%（最多 400 格）且纯度 < 0.45 |

### 4. 拼豆指引（核心）—— 一片区域一片区域地拼

工作单元是**连通色块（region）**，不是单粒（这一点和 [Zippland/perler-beads](https://github.com/Zippland/perler-beads)
的「专心拼豆」一致）：

- 每种颜色先按 4 连通拆成色块，面板给出「第几 / 共几块」「这一块多少粒」
  「第几–几行 · 第几–几列」，画布上用红色脉冲圈标出这一块的起手位置。
- 主按钮是 **✓ 这一块拼好了**（空格键）—— 一次标完整块。
  **也可以直接在图纸上点这一块里的任意一格**，同样会把整块标成完成；
  已完成的块再点一次可以取消（对应参考项目的 `handleCellClick`）。
- 色块优先级可切换（**拼块顺序**，默认「就近连续」）：

  | 方式 | 行为 | 适合 |
  | --- | --- | --- |
  | **就近连续（默认）** | 从最左上那块开始，每步走「包围盒空隙」最小的下一块，最后用 2-opt 消掉贪婪留下的长跳跃 | 手不用来回跑；整体自然从左上流到右下 |
  | 逐行扫描 | 严格按上边界、再按左边界，一行一行往下 | 想完全按方位来，最可预测 |
  | 离上一块最近 | 动态跟随你上一次落点 | 中途跳着拼、随时回到刚才位置 |
  | 大块优先 | 按面积从大到小 | 想先消掉大色块（但会满图跳） |
  | 边缘优先 | 贴着图纸外沿的先拼 | 从外围往里拼 |

  实测（83 个大小不一的色块散布在 90×60 图上）：

  | 方式 | 总移动距离 | 最大单次跳跃 |
  | --- | --- | --- |
  | 大块优先 | 2791 格 | 80 格 |
  | 逐行扫描 | 2843 格 | 80 格 |
  | **就近连续** | **606 格** | **18 格** |

  「大块优先」按面积排序、和位置完全无关，所以拼完一块下一块经常跑到图纸另一头；
  这也是最初默认值选错带来的问题。这条已经固化成回归测试（`npm run verify` 的最后一项）。

- 一块之内的下笔顺序可切换：蛇形（默认）/ 逐行 / 最近邻。
- 还提供「按单粒拼」模式，想逐粒记录时切过去即可。
- 其他操作：**整个颜色完成** / **撤销**（Ctrl+Z）/ **重拼本颜色**；一种颜色拼完自动跳下一种。
- 色块列表会标出哪些块已经完成，点任意一块可以直接跳过去。
- 颜色顺序可选「按位置（左上优先）」，配合就近连续能让整体走向更连贯。

#### 实拍/高密度图纸：两个「直接给答案」的入口

格内印满色号、格子又小（十几像素）的图纸，靠算法从像素里猜格距很容易被文字的
笔画间距带偏。这类图纸有两个更可靠的入口，都在校准页/「图纸」页：

**① 按标注格数校准（校准页）**

拼豆图纸的标题通常直接写着格数，例如「原神奥黛塔 [**104x104**/38色/共10816颗]」。
把它填进「按图纸标注的格数校准」，格距就退化成 `图案尺寸 ÷ 格数` 这个纯算术问题：

- 优先用图纸自带的**加粗分区线**（橙红色，每 N 格一条）定图案边界 ——
  横线横贯图案，它的左右两端就是图案的左右边界；竖线的上下两端就是上下边界。
  这比「内容包围盒」精确得多，因为包围盒会把外圈的行号/列号标尺和装饰边框也算进去。
- 分区线间距还给出一把高精度尺子，把格距吸附到 `间距 ÷ 整数`（这张图纸是 68/5 = 13.60px）。
- 没有分区线时退回「内容占比包围盒」，并尝试裁掉纯色的标尺/边框。
- 相位再用「色块边界」剖面精修。

实测某实拍图纸（1440×1710 JPEG、格距 13.6px、格内印满色号、自带行号/列号标尺与红色分区线）：

| | 自动识别 | 按标注格数校准 |
| --- | --- | --- |
| 格距 | 13.59 × **10.60** px ✗ | **13.60 × 13.60** px ✓ |
| 原点 | 13.1, 215.0 ✗ | **26.5, 242.5** ✓（实测真值 27, 242） |
| 行列 | 104 × **55** ✗ | **104 × 104** ✓ |
| 总格数 | 5720 ✗ | **10816** ✓（与图纸标注的「共10816颗」一致） |
| 识别出的颜色数 | 116 ✗ | **32**（图纸标注 38） |

自动识别失败的根因：格内色号文字的横笔画间距只有约 5.4px，而真实格距是 13.6px；
自相关先锁到 2 倍频 27，再在约数候选里被 27/5 = 5.4 骗走 —— 真实格距根本不在候选集里。
现在两轴会互相印证（豆板是方的），但最可靠的仍然是直接告诉它格数。

**③ 如果图纸用了大量接近白色的豆子**

这类图纸（浅蓝/浅粉/近白配色）会被「贴边空白当作不拼」误伤：
实测 10816 格里被划掉 1709 格。到「显示」页把那个开关关掉即可，
它们会按识别出的颜色重新算作豆子。

**② 按图纸图例约束色板（「图纸」页）**

图纸底部的色号表列出了这张图纸**真正用到**的颜色。把那些色号粘进去，
匹配范围就从 291 色收窄到这些颜色：

- 色号按当前选的**品牌体系**解析（同一个色号在不同品牌是完全不同的颜色，
  MARD 的 `A06` 和 COCO 的 `A06` 不是一回事），指定品牌里找不到才去别的体系找并提示你；
- 完全无法识别的色号会**单独列出来**，不会静默匹配错；
- 某格与候选色号都差得较远（> 14 ΔE）时回退到全色板，并告诉你有多少格回退了
  —— 这通常说明图例没抄全或抄错了。

> **色号显示不补前导零**：`D01` 显示成 `D1`、`H07` 显示成 `H7`（`C10`、`ZG1`、`IC04`→`IC4` 同理，
> 只去掉**数字部分**的前导零）。列表、指引面板、画布格内文字、CSV/图导出一致。
> 但这个规则**只影响显示**：粘贴图纸上印的 `C07` 还是显示后的 `C7` 都能认出来，
> 两者解析到同一个颜色（回归测试里有断言，也顺带检查了「同一品牌内规范化后不撞车」——
> 万一两个色号规范化成同一个键，索引会静默丢掉一个颜色，非常难查）。

实测同一张图纸：116 色 → **53 色**（图纸标注 38 色）。剩下的差距主要来自我目视抄图例时
看错了几个小字；把图例抄准会进一步收敛。

#### 识别质量：把不确定的地方摆到明面上
每格的采样纯度都会留着。纯度偏低的格子会：
- 在画布上用**琥珀色虚框**标出来；
- 在「图纸」页给出数量，并提供「跳到第 N / M 个」逐个核对。

图纸压得比较狠、有水印、或者某格正好压在网格线上时，这里就是该看一眼的地方。
（从本地进度恢复时无法重新评估纯度，这一项会显示 0 —— 重新上传同一张图纸即可重新评估。）

### 5. 进度保存与恢复
- 进度自动存进 **IndexedDB**（连同图纸原图、全部参数），关掉页面下次接着拼。
- 首页列出所有项目，点「继续拼」回到上次的位置；进度也会实时回写到卡片上。
- 拼到 100% 自动归入「已完成」，但**不会被删**；随时可以点开查看或取消完成。
- 「导出进度 JSON」可以单独备份/分享某一份进度。

### 6. 导出
- **识别结果 PNG**：把识别出来的格子导出成带色号的图纸，用来核对识别对不对。
- **采购清单 CSV**（带 BOM，Excel/WPS 直接打开不乱码）。
- **采购清单图 PNG**：色块 + 色号 + 数量 + 已拼。
- **进度 JSON**：可备份 / 分享。

### 7. 五套色号体系
内置 291 种标准拼豆色，覆盖 **MARD / COCO / 漫漫 / 盼盼 / 咪小窝** 五个体系的色号，
右上角随时切换，整个界面的色号跟着变。

### 8. 没这个颜色怎么办
每个颜色行右侧的 ⊘ 可以「排除」该颜色，它会被**重映射到最接近的可用色**；
排除的颜色会出现在下方可恢复区，点一下就能恢复。至少会保留一种颜色。

### 9. 空白格
自动判断「颜色接近纸面背景 + 与图纸外沿连通」的格子为不拼区域（例如图纸四周的留白）。
这个判断可能把贴边的白色豆子误当空格，所以提供了一个开关：
在右侧「显示」里关掉「把贴边空白当作不拼」，这些格子就会按识别出的颜色算作豆子。

## 识别算法

拼豆图纸有两个特点让「认格子」比想象中难：

1. **格子里印着色号文字**。文字是深色短横线，会形成很强的、且与格距同周期的假信号。
   实测这些假信号的强度甚至**超过真格线**，用「梯度求和」这类度量会把相位整条带偏。
2. **大片同色区域**。相邻两格同色时，两格之间没有颜色差，靠「相邻像素差」根本发现不了格线。

所以这里的做法是：

### 第一步：细长脊剖面（`buildRunProfiles`）
对每个像素判断它是不是「细脊」：

```
isRidge(x, y) = |L(x,y) − L(x−3,y)| > m  且  |L(x,y) − L(x+3,y)| > m
```

- 用**左右**邻居判断脊 → 沿 y 统计 → 得到**竖线**剖面；**上下**邻居 + 沿 x 统计 → **横线**剖面。
- 要求「**两侧都不同**」：既能抓到浅灰格线压在深色格子上的情况（只比一侧深/浅的严格判据会漏掉），
  又不会在格线上下 ±3 像素形成一圈假脊（那一圈会把真峰值稀释掉）。
- 剖面值不是「最长连续长度」而是「**脊覆盖率**」：属于长度 ≥ 3 的连续脊的像素占比。
  原因很实际 —— 格线在**交叉处会被垂直格线打断**（交叉点上下 3 像素也是格线颜色），
  所以「最长连续长度」实际只有一个格子宽，反而没有区分度：
  实测图例里 95 像素的短格线比图纸 22 像素的格线「最长连续」还长，直接把阈值带偏。
  覆盖率只被交叉点挖掉 1 像素，仍接近 1，而格内文字只有约 40% 覆盖率，区分度足够。

### 第二步：自相关求周期（`estimatePitch`）
对剖面做归一化自相关，取第一个强度达到全局峰值 55% 的局部极大值，
再抛物插值到亚像素。自相关对孤立的强边缘（外框、标题）天然不敏感。

### 第三步：消倍频（`pickFundamental` + `harmonizePitches`）
自相关经常锁到周期的 2 倍甚至 7 倍（大片同色时尤其明显）。
- 在候选的 1/2…1/8 周期里，用「梳状得分」（格点处剖面均值）挑最小的、得分仍接近最大的那个。
- 两轴再互相印证：豆板是方的，所以若两轴周期差很多、而大的正好是小的整数倍，就把大的缩回来。

### 第四步：定相位 + 最小二乘拟合（`fitLines`）
在周期格点上搜最佳相位，再逐条做局部极大值微调，最后最小二乘拟合出**小数精度**格距，
并剔除偏离拟合线过远的点（图例表格的线就是这样被丢掉的）。

### 第五步：图纸范围 = 内容包围盒（`contentExtent`）
把拟合出的格距/相位铺满整张图，逐格取主色，凡是明显偏离纸面背景色的格子算「有内容」，
取这些格子的包围盒。图纸下方的**图例表格**里的细线占不满一格、格子主色仍是背景色，
因此会被自然排除；四周的空白留边也不会被算进图纸。

### 第六步：逐格取主色（`sampleCells`）
每格向内收缩 20% 后统计像素颜色的**众数**（5 bit/通道分桶，再取桶内均值）。
不取均值 —— 均值会被格内文字和网格线拉灰；众数几乎总是格子的填充色本身，
对抗锯齿、网格线、文字都非常稳。

### 第七步：读取格内色号（`chartOcr.ts`）
本地读取格内印出的 MARD 色号。内置带字符语义的像素字体与静态 Arial 字形模板，
不要求手机安装 Arial；程序还会验证图纸坐标栏的连续编号，学习本图的数字字形。
可靠读到的文字优先于标准色板颜色；同填色格子的识别结果可以互相校验。
不支持的字体、模糊字或不满足候选色号的结果会保留为待确认。
识别证据与项目一起保存在 IndexedDB，重开项目后仍可核对。

文字不能可靠解码时，以 **CIEDE2000** 色差给出颜色候选，并保存第二候选和差距。
颜色排名按完整 24 位 RGB 缓存，默认逐格匹配，避免相邻真实近色被连通合并。
图纸软件的填色可能与公共色板不同，因此纯色填充并不意味着色号匹配一定正确。

### 第八步：空白格（`floodFromBorder`）
从图纸四边出发，对「与纸面背景色差 ≤ 9」的格子做洪水填充，
只有**与外围连通**的才算空格 —— 被图案包住的白色区域仍然算白色豆子。
有格内色号文字的格子受到保护；无法读清的白色格也保留并提示核对。
结果存成独立的掩码（不是直接把格子置空），所以随时可以一键关掉。

### 渲染性能

## 关于「用视觉大模型辅助识别」

DeepSeek 确实已经有能读图的模型。以下都是查官方文档核实的（2026-09-29）：

- `deepseek-flash` 接受图片输入 —— 官方 Vision 指南：
  <https://api-docs.deepseek.com/guides/vision>
  「The deepseek-flash model accepts images alongside text…」
- `deepseek-v4-pro` **不支持**视觉（定价页对照表里 Vision 一栏是「Not supported」）。
- 请求形态就是标准 OpenAI 兼容格式，`content` 是数组，
  图片用 base64 data URL 放在 `image_url` 里：

```json
{
  "model": "deepseek-flash",
  "messages": [{ "role": "user", "content": [
    { "type": "text", "text": "…" },
    { "type": "image_url", "image_url": { "url": "data:image/png;base64,…" } }
  ]}]
}
```

**但不要用它来读格子矩阵。** 这是官方文档里写死的限制，不是提示词问题：

> 图片会先按比例缩放，使其总像素数约等于一张 1300×1300 的图。
> 因此**每张图片最多 1024 个 vision token** —— 2000×2000 和 5000×5000 的图缩放后 token 数一样。

一张 104×104 的图纸有 10816 格，1024 ÷ 10816 ≈ **每格 0.09 个 token**，
一格连一个 token 的零头都分不到；而且**多传像素也换不来更多 token**。
再叠上误差累积：一万格要一次全对，需要每格准确率 >99.99%；
而视觉模型的错误往往是「自信地猜一个看起来合理的字符」，错得悄无声息，
这对图纸是最糟的失败模式（一张看起来完全正常的错图纸）。

**它真正适合的角色**（本项目的设计取舍）：

| 任务 | 用什么 | 为什么 |
| --- | --- | --- |
| 格距 / 原点 / 行列数 | **确定性 CV + 图纸自带的分区线与标注格数** | 栅格是强周期信号；图纸甚至把格数印在了标题上 |
| 每格色号 | **本地字形识别，颜色作为兜底候选** | 图纸印出的色号比不同软件的填色更可靠 |
| 色板范围 | **图纸图例的色号表** | 稀疏、有留白、条目有限，是视觉模型/OCR 的强项 |
| 识别不确定的格子 | **文字证据、颜色差距与人工核对** | 无法可靠读出的字形和候选冲突会保留提示 |

也就是说：视觉模型该用来读**图例色号表**和**标题里的格数**（然后填进上面那两个入口），
而不是用来产出格子矩阵。这两个入口目前都支持**手动粘贴/输入**；
接入 `deepseek-flash` 把这两件事自动化是下一步（需要 API Key，
并且要经过 Vite 代理绕开浏览器的跨域限制）。

如果你的图纸识别不理想，最有效的路径是**把那张图拿出来具体看**：
多半是网格没对准（校准页解决）、图纸被压缩/加水印（看低置信度格子）、
或者图纸本身是「色块图例 + 缩略图」的排版（需要框定图纸区域）。

## 已知限制

- **格内印满色号、格子又小（十几像素）的图纸，自动识别可能定不准格距**。
  这类图纸的自相关会被文字的笔画间距带偏（实测真实格距 13.6px 被锁成 5.3px / 21.2px）。
  现在两轴会互相印证，但最可靠的还是用校准页的「**按标注格数校准**」
  —— 格数就印在图纸标题上，填一下即可。
- **高密度图纸的颜色会有噪声**：格子越小，格内文字占的比例越大，逐格采样的众数就越容易被污染。
  实测 104×104、格距 13.6px 的实拍图纸，不约束色板会识别出 116 色（图纸标注 38 色）；
  用「按图纸图例约束色板」后降到 53 色，把图例抄准还能进一步收敛。
  「识别质量」里列出的低置信度格子就是需要人工核对的地方。
- **本地字形识别不是任意字体的通用 OCR**。当前针对清晰电子图中的 MARD 字母数字标签；
  极小字、特殊字体、严重压缩或遮挡仍可能需要人工核对。颜色兜底候选不保证正确。
- **没有印字的贴边白色格**仍可能被当成空白格。可在「显示」里关掉这个判断。
- 图纸若是**斜拍/有透视**，格子不是方形，需要先做透视校正，本项目暂不支持。
- 旧项目没有新增的字形证据，重新校准可以使用新流程；已保存的网格、进度保持兼容。
